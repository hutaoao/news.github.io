今天的主线是「工具链的攻与守」：Vite 的一个四月漏洞被自动化扫描舰队当成提款机，同时有人在用 Rust 把 Vite 的开发服务器整个重写。

### Vite 泄漏漏洞 CVE-2026-39364 遭大规模扫描：807 个攻击会话专挑 `.env` 与云凭证

F5 Labs 的蜜罐数据显示，2026 年 8 月针对暴露在公网的 Vite 开发服务器出现了持续的自动化扫描，共记录 **807 个攻击会话、约 32,000 条原始事件**，而此前三个月的基线只有 1,732 条——单月翻了约 18 倍。攻击入口是四月份披露的 CVE-2026-39364（CVSS 7.5）：在 `/@fs/` 请求上追加 `?raw`、`?import&raw`、`?import&url&inline` 之类的查询串，就能让 `server.fs.deny` 的拒绝名单检查被跳过，服务器以 HTTP 200 明文返回原本该被拦截的文件。

受影响区间是 Vite 7.1.0 至 7.3.1、以及 8.0.0 至 8.0.4，修复版本为 **7.3.2 / 8.0.5**。扫描器的词表相当专业：`.env.local`、`.env.production`、AWS 凭证与 SSO 缓存、`rootkey.csv`、`aws-exports.js`、Azure `accessTokens.json`、Terraform state 与 Serverless 状态文件，甚至用 `/proc/self/cwd/.env` 这种不需要知道安装路径的技巧来定位环境文件。请求还伪造了 Googlebot、ClaudeBot、GPTBot、PerplexityBot、OAI-SearchBot 的 User-Agent，并打入假的 `X-Forwarded-For`。同一批基础设施也在探 Next.js 的 CVE-2025-29927 中间件鉴权绕过。

值得注意的是来源分布：攻击流量主要来自 Google Cloud 的 34.x / 35.x 段，美国 17,297 条事件居首，其后是比利时、荷兰、新加坡、中国台湾、日本。**如果你有任何 `--host` 或容器端口映射把 5173 暴露到公网，现在就该轮换凭证，而不是只升级版本。**

_来源：[F5 Labs](https://www.f5.com/labs/articles/cloud-takeover-mass-scanning-for-exposed-vite-endpoints-cve-2026-39364)、[Field Effect](https://fieldeffect.com/blog/mass-scanning-exposed-vite-development-servers)_

### Node.js v26.9.0 发布：`node:bench` 落地，`ffi` 默认开启

Node.js 26.9.0（Current）同日发布，一次性塞进十一个 SEMVER-MINOR 变更。最值得关注的是 **`node:bench` 正式实现**（配合 `perf_hooks` 的 `Histogram.meanCI` 与直方图 CBOR 导入导出），基准测试终于不用再靠人眼看数字猜噪声。另外 `node:ffi` 从实验模块改为默认启用（Matteo Collina 主导），`crypto` 新增通用 MAC API 并能从 OpenSSL provider 动态发现 cipher 与 hash，`vfs` 打通了 CJS 与 ESM 模块加载器，`worker_threads` 开始支持 Web Workers 语义，还落地了实验性 DTLS API。

_来源：[Node.js 官方 Release](https://newreleases.io/project/github/nodejs/node/release/v26.9.0)_

### Lovable 开源 OJ：用 Rust 把 Vite 开发服务器重写了一遍

Lovable 内部把预览引擎从 Vite 换成了自研的 **OJ（Orange Juice）**，一个端到端 Rust 的单一二进制：从文件监听器到 WebSocket 都是 Rust，只在插件或服务端代码真的需要 JS 时才拉起一个小 Node sidecar。它直接读你现有的 `vite.config.ts`，通过兼容桥跑真实 Vite 插件，并重建了 React Fast Refresh 与 TanStack Start，底层站在 Rolldown 与 Oxc 上。

数字很直白——一万组件合成应用冷启动 1.2s（Vite 4.9s）、内存约 115MB（Vite >1.5GB）；Excalidraw 0.8s / 288MB（Vite 2.3s / 2.4GB）。生产环境里 Lovable 的预览总加载中位数从 17.4s 降到 8.0s，沙箱获取从 14.5s 降到 3.0s，dev server 进程内存少了约 6.5 倍。项目已从作者个人仓库迁到 `github.com/lovablelabs/oj` 开源。

不过 **Vite 作者尤雨溪当场提出质疑**：OJ 并不算完整重写，它建立在 VoidZero 的 Rolldown/Oxc 之上，只有 dev server 部分是 Rust；而且 Lovable 博客里 Vite 的冷启动数字包含了 `vite-plugin-checker` 在后台跑 tsc 的开销，OJ 并没有承载这个插件，两组数字并非严格可比。这个提醒值得记下：**「快多少倍」在工具链对比里往往取决于你算不算插件生态的成本。**

_来源：[Lovable Blog](https://lovable.dev/blog/faster-previews-oj)、[AGI Hunt 整理尤雨溪回应](https://agihunt.info/en/p/1a0a80c0b01520112fa64104e10)_

### Firefox Smart Window 接入 Mistral Small 4：Mozilla 用「模型可选」对抗浏览器 AI 垄断

Mozilla 与法国 Mistral 联合宣布合作，**Mistral Small 4 进入 Firefox Smart Window 测试版**：美国与加拿大用户可选用该模型，法国则同时扩大测试范围并首次提供官方法语支持，英国与德国预计年内跟进。Mistral Small 4 是一个 119B 总参数、约 6.5B 激活参数的开放权重模型——放到手机上跑不现实，但推理成本可控，适合面向全体浏览器用户开放的助手场景。

Mozilla CEO Anthony Enzor-DeMeo 的说法是「浏览器不该是一条单向漏斗」，Mistral CEO Arthur Mensch 则强调开源技术需要开放分发。隐私架构这次写得比较具体：Smart Window 全程 opt-in，只使用用户选择共享的标签页与历史；Mozilla 表示对话默认不落库、Mistral 承诺零数据保留，网页检索与来源展示交给同样主打隐私的 Exa。**值得注意的是行业并非一边倒**：Vivaldi 联合创始人 Jon Stephenson von Tetzchner 仍坚持「keep browsing human」，承诺永不在浏览器内集成 AI，这条路线分歧短期内不会消失。

### Schema.org 30.1 发布：纯增量加入欧盟产品护照与消费者告知

Schema.org 版本 30.1 于 9 月 16 日发布，**非破坏性、纯增量**，现有标记不会失效，验证器也不会开始报错。新增 `DigitalProductPassport`（数字产品护照）与 `EnvironmentalProductDeclaration`（环境产品声明）两个类，`Product` 上新增 `consumerNotice`、`isOftenBoughtWith`、`specification` 三个属性，另有 `minimumOrderValue`、`MaximumRetailPrice` 等运输定价术语，`MedicalSpecialty` 枚举补上 `Ophthalmology` 与 `Audiology`。

**一个必须说清的坑**：`DigitalProductPassport` 位于词汇表的「new」区域，官方明确定位为征集实现反馈，**发射它不会带来任何 Google 富媒体结果资格**——资格由 Google 搜索画廊决定，本次没有变化。所以只在你真的持有认证数据（认证机构、认证编号、到期日）时才写这段 JSON-LD。需要改动的地方是你的 JSON-LD 发射器，无论是手写组件、next-seo 还是 schema-dts 类型化构建器。

_来源：[Schema.org Releases](https://schema.org/docs/releases.html)、[Daily SEO Note 9/16](https://oday-bakkour.com/blog/seo-note-september-16-2026)_

### Chrome 把「广告负载」变成公开指标：CrUX 新增四个实验性字段

Chrome 把广告相关的性能数据送进了 CrUX API：**`experimental_ad_count`（广告数量）、`experimental_ad_density`（广告密度）、`experimental_ad_cpu`（按 CPU 的广告权重）、`experimental_ad_kilobytes`（按网络的广告权重）**。它们已经在 `queryRecord` 端点的 `metrics` 数组与 `queryHistoryRecord` 的每周时间序列中可用，同时出现在 DevTools 的 Ad 面板与 CrUX Vis 里。Ad Density 的测法是对整次访问每秒采样一次可见视口，报告广告框覆盖的平均视口面积占比——数据全部来自真实用户。

三条限制必须记住：**它们不是 Core Web Vitals 的一部分**；Google 没有给出建议目标或阈值；BigQuery 侧仍标注为「计划但未发布」。换句话说，**不要把它们接进会让构建失败的 CI 门禁**，放在 LCP/INP/CLS 旁边做趋势观察即可。对内容型站点来说，这次变化的真正含义是「你的广告负载现在是一个任何持有 CrUX API key 的人都能拉到的公开数字」。

_来源：[Chrome for Developers](https://developer.chrome.com/blog/crux-ad-metrics)、[指标文档](https://developer.chrome.com/docs/ads/metrics/density)_

### Nodemailer CVE-2026-92595：旧签名绕过沙箱，任意文件读 + SSRF

Nodemailer 9.1.0 及更早版本存在一个沙箱绕过（CVSS 4.0 评分 6.0 / CVSS 3.1 评分 5.9），**根因是 `MailMessage.resolveContent()` 的旧三参数签名**。当插件或应用代码用 `resolveContent(data, key, callback)` 这种文档里仍在写的老写法解析不可信内容时，`shared.resolveContent()` 会把缺失的 `options` 归一化成空对象，构造函数复制进 `mail.data` 的 `disableFileAccess` / `disableUrlAccess` 标志被丢弃，`resolveContentValue()` 于是跳过了两道访问控制检查，直接走到 `nmfetch(url)` 或 `fs.createReadStream(path)`。

结果是可以被诱导读取任意本地文件、或发起出站 HTTP(S) 请求（SSRF）。**`transporter.sendMail()` 内部走的 `resolveAll()`、`_convertDataImages()` 与 MIME 流式路径不受影响**，所以普通发信流程是安全的——风险集中在自定义插件和二次封装的邮件模板逻辑上。修复版本为 **9.1.1**。

_来源：[CVE-2026-92595 官方记录](https://www.cve.org/CVERecord?id=CVE-2026-92595)、[Rapid7](https://www.rapid7.com/db/vulnerabilities/cve-2026-92595/)_

### node-opcua CVE-2026-69200：`fieldsToJson()` 原型链污染

同一天披露的还有 node-opcua 的一个原型污染漏洞（CVSS 3.1 评分 3.7，CWE-1321）。`packages/node-opcua-client/source/alarms_and_conditions/client_alarm.ts` 里的内部方法 `fieldsToJson` 直接赋值未消毒的字段名，允许 `__proto__.pollutedKey` 这样的路径改写 `Object.prototype`。触发条件是应用把攻击者可控的事件字段喂给 `fieldsToJson`，后果是拒绝服务或应用逻辑被篡改。修复版本为 **node-opcua-client 2.145.0**。

_来源：[CVE-2026-69200](https://cve.report/CVE-2026-69200)、[GitHub Advisory GHSA-cv5q-7543-48q4](https://github.com/node-opcua/node-opcua/security/advisories/GHSA-cv5q-7543-48q4)_

### Gemini 3.8 Live 与 Extended Thinking：把「边说边想」做成默认，语音质量 82.6 分登顶

### 支付宝详解 xUI 引擎：从原生渲染 Markdown 到 A2UI 生成式渲染的三代演进

InfoQ 刊出蚂蚁集团支付宝 AI 端云交互负责人魏凤笛的分享实录，系统拆解了支撑「阿宝」的 **xUI 引擎**。它对前端同学最有价值的部分是那条清晰的渲染技术演进线：**第一代**基于 Markdown 做三端原生渲染，为了 AI 感而放弃引入浏览器引擎（前端渲染实现简单但工程成本高、稳定性差）；**第二代**因为模型能生成复杂 HTML，转向自研 Web 内核并对 MY Web 与 WKWebView 做深度优化，在原生对话界面里嵌入 Web 区块；**第三代**引入 Google 的 A2UI 概念，不再让模型生成页面，而是让模型输出「要做什么事」，再通过工程上的标准组件与操作协议翻译成可交互 UI 卡片。

架构上，xUI 覆盖全双工多模态通信、生成式渲染、服务执行与多 Agent 协同四个方向，采用异步任务调度与「伴随式交互」支持长周期事务，多 Agent 按角色与能力分层编排。**这套思路对所有做 AI 原生界面的团队都有参考价值：真正的难点不是把 LLM 输出渲染出来，而是让表达层与 Agent 层通过协议解耦。**

### OpenAI 爬虫名单增加到四个：robots.txt 需要为 OAI-AdsBot 单独写具名组

OpenAI 的爬虫名单现在包含四个独立身份，**必须当作四个独立决策**来对待：`GPTBot`（生成式模型训练）、`OAI-SearchBot`（在 ChatGPT 搜索中呈现站点）、`ChatGPT-User`（用户触发的单次抓取）、以及新增的 **`OAI-AdsBot`**（验证广告落地页是否符合 OpenAI 广告政策，**不喂训练**）。文档地址也从 `platform.openai.com/docs/bots` 301 迁移到了 `developers.openai.com/api/docs/bots`，runbook 与书签需要一并更新。

两个容易踩的细节：OpenAI 为 gptbot、searchbot、chatgpt-user 发布了 IP 范围文件，**但 `OAI-AdsBot` 没有，目前只能靠 User-Agent 匹配**；robots.txt 的改动大约需要 24 小时才会在 OpenAI 系统内传播完毕。按 RFC 9309，最具体的 UA 匹配胜出，所以具名组会击败通配符 `*`——**如果你的 robots.txt 只有一条通配规则，那现在广告验证与搜索可见性都在被这条规则替你决定。**
